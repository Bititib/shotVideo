# 批量视频

入口：工作台 → 批量视频（`/app/video-batch`）。本功能使用网站登录账户，沿用个人/组织余额预扣机制，不使用浏览器 API Token 额度。

## 使用

1. 选择模型、时长、比例、分辨率。
2. 添加 1–20 组创意，每组填写原始提示词、图片/视频/音频参考与数量，总计最多 100 条。提示词不会自动改写。
3. 按需开启“确认失败后自动重新生成”，默认关闭；开启默认重试 2 次，最多 3 次。
4. 校验并预估费用，再确认整批预扣。可关闭页面，后台持续排队、查询并恢复进度。
5. 成功视频可以预览、单独下载或打包 ZIP。缓存沿用现有保留期限，过期文件需先恢复；单个 ZIP 上限 3 GiB。

## 计费与失败语义

- 创建批次与预扣在同一 SQLite 事务内；重复请求标识不会再次预扣。
- 每个逻辑视频保留一份预扣，自动重试的内容记录费用为 0；最终成功的内容记录结算该份预扣，不再次减少余额。
- 已确认失败且重试耗尽、参数/审核拒绝、取消未提交任务时原路退款。组织余额扣款会退回原组织；组织已删除时沿用个人余额兜底逻辑。
- 关闭自动重试会退还正在等待重试的任务；正常待提交任务继续，执行中的任务继续但之后不再自动重试。
- “重试失败项”是用户主动发起的新一轮生成：因之前已退款，需要重新预扣，界面会再次确认；操作也有幂等标识。
- 查询超时、HTTP 502、HTTP 200 内嵌查询错误、完成但暂时无链接，均不作为再次生成的依据：继续查询原任务。
- 提交 POST 超时/5xx、或服务器在 POST 后保存任务 ID 前中断，无法证明上游没有接单。任务进入“待核实”，保留预扣，不重复提交，也不直接退款。管理员需核对上游，不能把这种状态当成已确认失败。
- 管理中心可筛选“待核实”。有原上游 ID 时可以重新获取结果：成功结算原预扣，确认失败按批次策略处理。没有保存上游 ID 的记录需要人工向上游核实，系统不会猜测任务 ID 或补发。
- 旧的“一键恢复近三天失败视频”排除批量尝试，避免恢复已经被重试替换的旧任务和重复扣款。

## 调度与部署

继续使用项目现有 SQLite 数据目录与单应用进程部署方式；新增表通过批量服务加载时幂等创建，无需手动修改已有表。

默认全站最多 6 个批量执行任务、每用户最多 3 个。可通过 `VIDEO_BATCH_MAX_ACTIVE`、`VIDEO_BATCH_USER_ACTIVE` 调整（范围 1–20），HM 仍受现有 Key/渠道队列限制，其他渠道先检查配置容量。没有配置非 HM 容量时按 1 个处理。并行只减少批量操作等待，不保证上游成功率或固定完成时间。

后台每 5 秒扫描批次；服务重启后恢复已记录 ID 的原任务，已开始提交但没有 ID 的任务进入待核实。占用中的“待核实”任务仍占调度名额，防止不确定任务不断叠加。

单用户最多同时持有 200 个未结算逻辑任务。队列限额和内部一次性凭证按单进程设计，不支持直接用多个 Node 进程同时启动同一 SQLite 调度器；水平扩容前需增加分布式租约与共享调度。

服务器必须能访问自身 `127.0.0.1:PORT`，并配置外网可访问的 `BACKEND_URL` 供参考素材使用。Docker 沿用当前持久化 `data` 卷；更新前备份数据库与上传文件。

## 验证

新增测试使用内存 SQLite / 模拟上游，不触及真实用户余额，不调用真实生成接口：

```text
npm test -- tests/videoBatchStore.test.ts tests/videoBatchService.test.ts tests/videoBatchRoutes.test.ts tests/videoBatchArchive.test.ts tests/videoBatchPage.test.tsx
npm run lint
npm run build
```

上线后建议先用测试账号提交 2–3 条做渠道验收，核对预扣、成功实扣、最终退款，以及重启后不重复生成。真实上游验收尚不能由单元测试替代。
