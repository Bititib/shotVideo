# 模型与渠道接入准则

版本：1.0  
生效日期：2026 年 10 月 24 日  
适用范围：新增模型、新增渠道、更换供应商，以及接入相关的同步、API、提交、查询、恢复、计费和退款修改。

本准则用于防止模型只完成页面展示就上线、不同上游被笼统处理、明确失败误入待核实，以及重复生成和重复扣退费。以下要求是开发和验收要求，不代表平台现有全部渠道已经完成整改，也不代表已经建立自动化上线拦截。

## 一 接入前确认范围与证据

1. 先区分已有渠道增加模型、增加新渠道、更换供应商。已有渠道只可复用已验证且适用于新模型的协议部分；新模型的参数、终态和错误差异仍需核对。
2. 记录官方文档链接、读取日期、接口版本和适用模型。没有文档的关键行为，用脱敏真实响应及供应商明确说明作为证据，不凭模型名或错误文字猜测。
3. 至少确认鉴权、提交路径、请求格式、成功响应、任务 ID、查询路径、全部已知状态、错误结构、下载方式及计费单位。
4. 单独确认幂等键、回执查询、任务列表或回调是否存在及其保证范围。发出 `Idempotency-Key` 请求头，不等于上游承诺去重。
5. 新建接入验收记录；证据不足的字段标明“未确认”。不能把假设写成供应商规则。

## 二 模型身份与能力配置

- 平台公开模型 ID 不带供应商渠道前缀；内部执行 ID、渠道 ID 和上游真实模型 ID 分开管理。上游请求必须使用映射后的真实 ID。
- 对外 ID 必须唯一。去前缀后发生重名时，先核对能力、价格、权限和路由，不自动覆盖、合并或把两个不同产品公布成同一个 ID。
- 记录时长、步长或可选值、分辨率、比例、参考图片/视频/音频数量、素材大小及可组合限制。不得将系列中某一型号的限制套给整个系列。
- 用户提供的素材、时长、模型、画幅等不能为“重试成功”而静默删除或修改。无效输入应尽早返回具体原因。
- 模型同步只导入当前令牌有权限且协议已识别的型号。新模型默认停用；同步及重启不得覆盖管理员已确认的售价、启用状态和自定义配置。
- 上游成本与平台售价分开。明确按次、按秒、按输出、Token 或其他单位，不把上游报价自动作为平台售价。
- 公开名称变更须明确旧 ID 的策略：兼容、迁移或停止调用。按用户决定执行；停用旧 ID 时返回明确错误和可用替代名称。

## 三 各渠道必须独立解释协议

“禁止对上游 API 进行统一笼统的错误处理，必须针对每个上游返回独立详细报错。”

可共用 HTTP 客户端、字段脱敏、任务持久化、事务账本和调度机制；但业务码、状态映射、提交是否受理、可否重试及退款证据，必须属于具体渠道和具体操作。

同一个 HTTP 状态或同名字段在不同渠道可能含义不同。提交接口、查询接口、下载接口也不能共用同一套“成功或失败”推断。代码中必须能追溯判定依据；特殊文案规则只适用于已确认渠道，不全局匹配提示词或任意嵌套文本。

## 四 提交与任务状态判定

| 情况 | 必须采取的行为 |
| --- | --- |
| 本地参数校验失败或能够证明请求未发送 | 返回具体原因；如已有预扣，按事务规则退回；不进入上游轮询 |
| 当前渠道明确拒绝提交 | 保存原始业务原因及脱敏诊断，结束本次订单，预扣只退一次；不得仅因缺少 ID 保留待核实 |
| 返回有效生成任务 ID | 立即持久保存原渠道、执行 Key 标识和任务 ID；检查即时状态，再查询原任务 |
| 返回受理编号但尚无生成任务 ID | 按该渠道受理查询协议继续等待；不得将 submission_id 当作 task_id |
| 查询成功且任务明确失败或取消 | 按渠道终态及计费约定结束任务；保留失败原因；不得因为存在 error 对象将其当查询异常 |
| 已有任务 ID，但查询接口超时或报错 | 保留 ID 和原渠道，按规则退避查询；查询报错不等于生成失败 |
| 生成完成但成品仍在保存或下载暂时失败 | 继续处理原结果，不再次生成，不直接按生成失败退款 |
| 提交响应丢失、不完整或回执冲突 | 先执行已确认的恢复机制；无法确认受理结果时才保留待核实，禁止盲目重发或按等待到期退款 |

必须对队列进入、开始发送、收到响应、保存 ID、开始查询等实际代码位置进行核对。不能仅根据状态名称推断执行顺序。本地 `processing` 可表示正在执行提交，必须有元数据或独立状态区分“提交进行中”和“上游已受理”。

不得以“没有任务 ID”单独判断失败或人工核实。明确拒绝本来就可能没有 ID；受理处理中也可能暂时没有生成 ID。

## 五 并发 重试与恢复

- 付费提交前保存本地订单及逻辑请求编号，并建立提交占用保护，防止重复点击、并发处理和恢复扫描重复发送。
- 支持幂等保证的渠道，保存原键及必要请求快照。允许重放时必须使用原键、原身份和相同请求，且遵守该渠道保证范围；不能换键“重连”。
- 优先使用只读回执查询找回原任务。`accepted`、`processing`、`rejected`、未知状态等按渠道协议处理，不能把 HTTP 404 一律解释为从未提交。
- 用户刷新或关闭页面不能中断后台提交。拿到 ID 后立即持久化；服务重启后查询原任务，不重新执行生成 POST。
- 依据渠道文档设置提交超时、查询间隔、退避和 `Retry-After`。延长超时不能代替回执恢复。
- 临时并发满载不应永久停用渠道或 Key。故障隔离与管理员停用应分开表达。
- 切换备用线路前，必须确认上一条请求没有仍在执行的生成任务。新请求不得继承上一请求的拒绝或退款标记。
- 恢复使用原渠道和原执行身份。缺少原密钥、回执或协议支持时，保留具体原因与管理员处理入口，不谎称自动恢复成功。

## 六 计费与订单一致性

- 预扣、提交、成功结算、失败退款和恢复处理必须有可追溯关联；关键更新采用事务及重复执行保护。
- 多次轮询、重复回调、并发恢复或重复读取不得造成重复扣费或退款。
- 上游业务失败、平台退款和上游退款到账分别记录。类似 `refund_flow_recorded` 的流程标记不是到账凭证。
- 查询失败、下载失败和受理结果未知不能直接触发退款；有明确协议保证的例外必须写明渠道和证据。
- 退款自身失败应标记为结算异常，不应伪装为提交未知。成品已成功也不能因保存或结算故障重新生成。
- 历史订单不得凭新文案规则批量改状态或退款。迁移与恢复必须依据原响应、原回执或账单证据，并与本次授权范围一致。

## 七 错误信息与用户界面

- 错误展示保留实际可获得的阶段、HTTP 状态、业务码、请求或任务编号及具体原因；不得仅显示“失败，请重试”。
- 不编造上游未给出的原因或素材索引。未知字段与无法解析的响应明确说明，保留必要诊断供核查。
- 对密钥、Cookie、授权头、签名链接、个人信息和素材进行脱敏。不能为展示“完整错误”泄露凭据或整段请求正文。
- 区分排队、提交处理中、生成中、保存中、明确失败和待核实。没有真实进度时，不伪造百分比。
- 前端列表、开发者页面、API 模型列表、价格查询、复制示例及实际请求解析必须一致。
- 未完成的后台入口不得随模型接入顺带开放。需要单独完成可用性验收后才展示。

## 八 必须完成的验证

每个接入记录列明以下场景的测试或不适用依据，不能只写“测试通过”：

| 验证项 | 验收标准 |
| --- | --- |
| 正常提交与完成 | 正确传参、保存 ID、查询、保存成品、结算 |
| 参数 鉴权 余额 限流 维护错误 | 按该渠道合同判定，具体原因保留 |
| 2xx 业务错误及即时失败任务 | 不误认受理成功，也不无限等待 |
| 非 JSON 响应 缺少 ID 冲突回执 | 不盲目退款、重发或认领其他任务 |
| 网络未建立与发送后断线 | 区分证据，恢复时不重复付费提交 |
| 查询错误与任务失败 | 两者不同处理；未知状态不猜终态 |
| 下载 保存与结算异常 | 保留原成果和订单，不重复生成 |
| 重复点击 回调 恢复 重启 | 只创建允许数量的任务，只扣退一次 |
| 定价 权限 名称及冲突 | 无越权路由，公开 ID 与价格、解析一致 |
| 旧渠道隔离 | 新规则不改变其他渠道同类响应的语义 |

先完成模拟上游与隔离数据库测试，再做经用户授权、明确额度的小范围真实验证。没有真实调用授权时保持模型停用，记录“生产验证待完成”，继续交付其余已授权代码工作。

运行与变更相关的类型检查、测试及构建。记录已存在的失败及证据；不得将局部通过写成全量通过，也不得隐去新增失败。

## 九 启用与交付门槛

启用前必须确认：协议与映射、能力限制、售价、权限、状态处理、计费、恢复、错误脱敏、页面/API 一致性、关键测试、生产验证及回退方案。适用检查未完成时保持停用，并说明缺口。

交付记录必须区分：代码已完成、测试已通过、已提交/推送、已部署、生产已验证。附提交号、更新方式、涉及的配置变更、迁移影响、已知限制和待办事项。

回退不仅是回退代码：须评估新旧模型 ID、渠道密钥、数据迁移及在途任务能否兼容。不得通过重新提交在途订单实施回退。
