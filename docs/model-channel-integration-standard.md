# Codex 渠道接入编码准则

版本 2.0　更新日期 2026 年 10 月 24 日

执行者是 Codex。用户说“接入这个渠道或模型”“修复待核实”时，你必须按本文完成代码工作，而不是回复一份流程让用户执行。本准则约束开发行为，不新增用户审批要求，不宣称系统已实现自动上线拦截。

## 先取得事实

- 自行读取用户提供的官方文档，核对当前版本、鉴权、提交路径、请求格式、任务 ID、查询状态、错误体、素材与下载方式。
- 已有渠道增加模型时，核对新模型与已验证协议的差异。新渠道不得因为“OpenAI 兼容”就省略独立核对。
- 文档打开失败时尝试可用的浏览器或公开文档入口，不将访问失败说成文档没有该功能。
- 区分文档事实、响应样本、代码现状和推测。信息缺失时继续完成不依赖它的工作，只补问真正必要的问题，不猜字段或要求用户重复提供已给资料。

## 修改前追踪实际执行顺序

先搜索代码，列出以下节点实际所在的文件与函数，并确认哪些入口会调用它们：

1. 请求模型解析、权限与参数校验。
2. 订单创建、预扣和进入队列。
3. 提交占用、开始发送、超时设置和异常捕获。
4. 响应解析、任务 ID 或受理编号保存。
5. 轮询、回调、结果下载与本地保存。
6. 成功结算、失败退款及重复执行保护。
7. 页面断开、进程重启、后台扫描和管理员恢复。

特别检查网站、外部 API、批量队列、销售规格路由是否走不同分支。修复必须落到实际执行路径；不允许只修改名义上的直接提交分支，遗漏真正处理订单的队列 catch。

不要把本地 processing 解释为已取得上游任务。检查它究竟在发送前还是响应后写入，并保证提交锁、恢复扫描和任务 ID 持久化之间不存在重复提交窗口。

## 编写渠道专属协议判定

必须落实用户规则：禁止对上游 API 进行统一笼统的错误处理，必须针对每个上游返回独立详细报错。

可以复用 HTTP 传输、诊断脱敏、持久化、调度和账本事务。业务错误码、状态映射、是否受理、能否重试和退款证据必须归属于具体渠道、接口和操作阶段。

允许将独立适配器的结果交给共同状态机，但必须保留区分信息，例如明确拒绝、已取得任务、受理处理中、提交结果未知，以及任务成功或失败。不要为所有上游写一个仅检查 error、HTTP 状态或 id 是否存在的通用判定。

| 读到的证据 | Codex 应实现的处理 |
| --- | --- |
| 本地校验失败或能证明请求未发送 | 不轮询；返回具体原因；已有预扣按账本规则退回 |
| 渠道明确拒绝提交 | 传递明确拒绝标记至最终订单处理；结束并幂等退款，不因缺 ID 转待核实 |
| 有效生成任务 ID | 立即保存 ID、原渠道和执行 Key 标识；检查即时终态后查询原任务 |
| 只有受理编号 | 调用该渠道受理查询，不将 submission_id 当生成 task_id |
| 回执仍在处理中 | 继续等待和查回执，不伪装成失败或永久人工审核 |
| 查询成功且任务明确失败 | 作为任务终态处理；即使响应带 error 对象，也不当作查询接口故障 |
| 已有 ID 但查询接口报错 | 保留原 ID；按渠道约定退避，不因此退款或新建任务 |
| 成功但结果保存中或下载暂时失败 | 继续保存原结果，不重新生成 |
| 提交断线、响应不完整或证据冲突 | 优先恢复原回执；无法确认时保留具体待核实原因，不盲目重发或退款 |

HTTP 200 不一定业务成功，HTTP 500 不一定受理未知。必须读取当前渠道的完整已确认错误结构。比如 snumom 的 build_request_failed 规则不能套到其他渠道；HUSS 的拒绝回执也不能替代 HM 的提交约定。

未知状态不得猜成成功或失败。错误文字匹配只能针对已确认渠道的指定错误字段，不能搜索提示词、HTML 或任意嵌套文本得出退款结论。

## 保留详细错误并保护敏感信息

- 将上游业务码、具体原因、操作阶段，以及实际可取得的 HTTP 状态、请求或任务编号贯穿适配器、服务、数据库和前端/API。
- 上游未返回原因时明确说未提供，不编造素材索引、失败原因或“请重试即可”的结论。
- error、message、detail、fail_reason 等字段按各渠道定义读取。外层 catch 不能再次把已解析原因替换为固定文案。
- 对密钥、Cookie、授权头、签名链接、个人信息及素材脱敏。不能把整段请求或网页当“完整错误”直接暴露给用户。
- 分开记录提交未知、查询异常、结果保存异常和结算异常，便于恢复，不能全部叫作同一种待审核。

## 实现恢复而非重复生成

- 付费提交前保存订单和逻辑请求编号，使用现有提交占用机制防重复点击、队列并发和恢复扫描重复发送。
- 只有上游明确支持时才依赖幂等键；保存原键和必要的请求快照。发送了同名请求头，不等于已经具备去重保证。
- 优先调用只读回执查询。恢复使用原渠道、原身份和原编号。缺少生成 ID 时不得调用任意任务查询，更不能生成新编号盲目重提。
- 只有文档明确保证安全且符合业务授权，才重放相同请求。处理受理编号冲突时先核对原请求。
- 页面刷新和浏览器断开不应中断后台提交。取得 ID 后及时持久化；服务重启继续原任务。
- 根据文档设置查询间隔、退避和 Retry-After。延长提交超时不能替代找回机制。
- 临时并发限制不得永久停用渠道或 Key。切换备用线路必须有上一请求明确未继续生成的依据，新尝试清除上一尝试的拒绝标记。

## 保证资金处理与状态一致

- 沿用经过验证的事务账本；新增分支也必须进入同一幂等结算路径，不能各自直接增减余额。
- 验证重复查询、回调、恢复和并发执行只扣退一次。错误判断不能落在保存受理证据之前。
- 区分上游失败、平台退款、上游退款到账。不能把 refund_flow_recorded 这种流程标记当到账证据。
- 查询失败、下载失败或受理未知不能自动退款，除非该渠道有明确适用的保证。
- 已成功结果遇到结算异常时保留结果；退款异常记录为结算问题，不能再次生成。
- 不根据新错误文案批量改写历史订单；历史处理依赖原响应或回执证据及已有授权。

## 接入模型时保持产品数据一致

- 对外 ID 不带渠道前缀，内部映射到上游真实 ID。重名时查清已有产品身份，不自行加供应商前缀、合并价格或覆盖权限。
- 核对每个型号的时长、步长、比例、清晰度、素材数量和组合限制，不复制整个系列的统一上限。
- 不为让请求成功而静默删素材、降分辨率、改时长或切换模型。
- 同步新模型默认停用；不覆盖管理员已设置的价格和状态，不把上游成本自动作为本站售价。
- 页面、模型 API、价格查询、复制示例、请求解析和返回值必须一致。模型下架或改名时遵循用户指定的兼容策略，不擅自保留或删除旧调用方式。
- 不顺带开放未完成的后台功能，不借接入任务扩大无关界面改造或数据库迁移。

## 用测试证明修复的是实际问题

对于状态、资金和恢复变更，补能暴露原错误的测试，不写只重复实现逻辑的断言。至少按适用范围覆盖：

- 正常提交到完成，以及提交立即返回失败终态。
- 各渠道明确参数、鉴权、余额、限流和维护错误。
- 2xx 业务错误、非 JSON、缺少 ID、嵌套 ID 和冲突回执。
- 请求未发送、提交后断线、查询暂时错误、未知状态。
- 保存失败、结算失败、重复执行、重启恢复。
- 明确拒绝不误入待核实，未知受理不重发，退款一次性。
- 新规则不影响其他渠道同名错误。
- 公开 ID、映射、定价和权限一致。

除适配器单测外，涉及队列和资金的修改必须验证实际队列或服务入口及隔离账本。先模拟验证，再在已有授权范围内进行真实验证；不擅自消费上游余额。没有真实验证授权时继续完成本地代码与测试，明确该项尚未验证，不要求用户为了接收代码另行批准整套流程。

运行相关类型检查、测试和构建，记录实际范围及失败。既有失败要核实来源，新增失败要处理；不把局部通过说成全量通过。

## 自行完成交付

由 Codex 记录关键协议依据、实际修改路径、测试结果和剩余限制。可使用 [开发记录模板](model-channel-integration-template.md)，也可更新现有接入文档或提交说明；不强制用户填表，不为简单修改制造重复文档工作。

完成用户已授权的修改、提交及推送。是否启用、部署、真实付费验证按用户已有要求和授权执行，不因为本准则新增重复确认。

交付时说明改了什么、为什么、验证了什么、哪些仍未知，区分代码、测试、推送、部署和真实验证。不得用“已检查”替代“已修复”，也不得承诺所有未见过的上游响应都已解决。
