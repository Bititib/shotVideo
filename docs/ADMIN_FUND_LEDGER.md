# Administrator fund ledger

The admin menu exposes /admin/fund-ledger. The API /api/admin/fund-ledger requires a signed-in platform administrator; organization administrators and ordinary users cannot read it. No new balance-edit endpoint is introduced.

SQLite triggers record actual balance changes to users, organizations and api_tokens in the same transaction as the mutation, including legacy direct SQL. The common balance/token services provide charge/refund/recharge context; admin balance edits and billing reconciliation provide administrator IDs. Older call sites without operation context are labelled as other increases/decreases. Known content IDs are propagated through website/API precharges, refunds, settlements and recovery. When a reservation precedes content creation, exact audit entry IDs are captured within the deduction transaction, persisted in its context and bound after content creation. Entries from another task cannot be overwritten. Missing historical IDs are never inferred from time or amount.

Existing balances are recorded once as opening snapshots without changing money or inventing historical transactions. New accounts receive an initial-balance entry. Repeated startup does not duplicate opening entries. Account deletion does not delete ledger history. Failed/rolled-back mutations do not produce committed movement entries. This is an audit layer; existing charge/refund idempotency rules remain responsible for preventing duplicate business operations.

Token quota is distinct from user/organization money. Switching to or from unlimited quota is a mode event with no cash delta. The separate account type `token_usage` records actual `used_amount` changes for both unlimited and finite tokens in the same SQLite transaction. A charge increases this counter; a refund decreases it. Raw SQL changes with no trusted service context are labelled as other usage increases/decreases, not inferred charges. A refund clamped by existing business logic records only the actual counter reduction. This audit layer does not change pricing, refund rules, account balances or existing cumulative usage. Never add usage-counter deltas to wallet or remaining-quota deltas.

At first enablement, existing counters receive zero-delta `usage_opening` snapshots and a separate `token_usage_started_at` marker. New tokens receive zero-delta `usage_initial` snapshots. These values are baselines, not historical consumption; missing historical changes are not reconstructed. Repeated initialization does not duplicate snapshots. No API keys or raw request bodies are stored. Usage audit failures roll back together with the corresponding account mutation.

The UI defaults to wallet movements (`scope=wallet`); Token usage (`scope=usage`) and remaining quota (`scope=quota`) are separate keyboard-accessible views. The legacy API default without a scope remains all records for compatibility. Filters support owning user ID (`userId`), exact local content ID (`contentId`), account type/ID/name, movement type and inclusive Beijing calendar dates, with server-side pagination. Clicking a task keeps the current view and filters by that task. Current local and upstream task IDs are projected from known content/receipt fields without exposing prompts, API keys or large media metadata. Repeated real charges stay as separate entries; neither identical amounts nor timestamps are proof of duplication.

The audit-only `fund_ledger_content_links` table supports one batch debit associated with multiple generated tasks. A batch amount is displayed once with an expandable task group; it is never repeated per task or relabelled as a unit price. Batch item refunds link to their own content IDs when available. User filtering uses the stored owner or an explicitly linked content owner; shared organization movements without task attribution are not guessed. Deleted content IDs remain visible. There is no historical backfill, balance repair, price migration, payment-provider receipt matching, CSV export or ordinary-user ledger. No new provider generation call is introduced.
