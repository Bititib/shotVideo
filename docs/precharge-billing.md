# 生成请求预扣费规则

按后台模型价格，在调用生成服务前预扣余额；余额不足时不调用模型。以下为本次统一的范围：

| 入口 | 处理方式 |
| --- | --- |
| 网站与画布图片生成 | 按请求张数预扣，按成功张数结算，失败部分退款 |
| 旧版图片生成、语音合成 | 请求前预扣，成功结算，失败退款 |
| 开放 API 图片生成、图片编辑 | 请求前预扣，返回有效图片后结算，失败退款 |
| 开放 API 对话 | 按输入估算与最大输出数预扣，收到实际用量后退回差额 |
| 开放 API 视频 | 生成提交前扣款，异步失败继续使用原视频退款流程 |

视频与批量视频沿用原有预扣机制。分析类每日次数配额、模型列表、价格查询、任务状态查询不新增余额收费。

## 账务保护

- 预扣与账单写入在同一数据库事务中完成。
- 个人、组织、有限 API Key 均检查当前余额后原子扣款，阻止同时请求造成透支。
- 图片沿用提交时价格；对话预扣与结算使用同一价格快照。
- 新增预扣记录的结算、差额退款、全额退款具有幂等保护；已经结算的记录不会被错误处理分支再次退款。
- 保存原扣款来源；用户切换组织后，退款仍退回原来源。
- API Key 累计消费在退款时同步冲回。

## 待核对情况

`billing_reservations` 保存 `amount`（预扣）、`actual`（已知实际费用）、`state`、`receipt`（原扣款来源）与 `context`（用户、API Key、模型或内容关联信息）。

- `reserved`：任务运行中；也可能是进程中断后未完成结算的记录。
- `settled`：完成结算。
- `refunded`：完成全额退款。
- `review`：上游未返回对话用量，或实际费用超过预扣金额。保持原预扣金额，不将未知用量伪装成已结算费用，也不自动追加扣款。

非流式对话返回 `X-Billing-Status`，对话请求返回 `X-Billing-Reservation` 供定位账单。流式请求的最终账务状态以预扣记录和 API 日志为准。

后台新增“异常账单”入口：超过 24 小时的 `reserved` 列为待核对，不自动退款。管理员核对上游结果和用量后填写实收与依据，事务内原路退回差额，并记录审计日志。旧视频任务继续沿用原任务恢复和退款机制。不要仅凭等待时间就退款，也不要直接重发生成请求。

## 验证

`tests/billingReservation.test.ts` 与 `tests/prechargeRoutes.test.ts` 使用内存数据库和模拟上游，覆盖个人/组织/API Key、并发余额竞争、部分成功、退款幂等、事务回滚、图片/TTS/对话接口预扣顺序和流式用量跨包解析。测试不接触真实账户与付费模型。
